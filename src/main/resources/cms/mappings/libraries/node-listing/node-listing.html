NodeService list and enumerate

XP 8.1 gives NodeService two methods for reading a subtree in path order. list streams every entry, so nothing has to hold the whole subtree, and enumerate returns the same entries one bounded batch at a time with a cursor. ListNodesResult and its recursive flag are gone. They do not treat access the same way, which the checks below settle.

Neither is exposed to JavaScript, and deliberately so: they are built to walk millions of entries, a workload where JavaScript is an unacceptable performance hog. Java is therefore the only way to reach them, so this test goes through a script bean, com.enonic.xp.sample.features.NodeListing — the only test in the app that needs one.

The two differ on access. list sets a required permission on its query, so it returns only the entries the caller may read and needs no special role. enumerate calls requireAdminRole and then queries without a required permission, so it returns every entry in the subtree and is available to administrators only. That suits what it is for: a resumable snapshot scan, with modifiedBefore as a cutoff, a version id per entry and a cursor to continue from. An export or a dump that silently skipped unreadable nodes would look complete while being wrong.
