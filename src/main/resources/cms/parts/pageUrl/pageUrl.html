Cross-context calls

Naming another project or branch asks for a URL the request cannot supply, so these are resolved from content alone. They are anchored to the base URL of the target's nearest site when it has one, and otherwise fall back to the site service path, /site/<project>/<branch>/..., which is not a public address. This is the pair whose result does not follow the vhost.

Treat these two as unstable. The behaviour is still settling, and what these rows expect is drawn from what the platform currently does rather than from anything specified. Three things are known to be unresolved. A nested site inherits nothing, so a subsite without a base URL of its own falls back to the service path while its parent resolves correctly. The base URL and the path are not always taken from the same site, which produces an address that looks right and resolves nowhere. And the service-path fallback is indistinguishable from a working URL, so a missing configuration surfaces as a wrong answer rather than as an error. Expect these expectations to change.
